# ROS 2 Project Contributor Guide

## Environment and goal

- Target environment: Ubuntu 24.04 with ROS 2 Jazzy.
- Primary language: C++.
- Tooling: VS Code, CMake, and colcon.
- Goal: build a portfolio-quality ROS 2 computer-vision project using the laptop webcam.

## Repository layout

- `src/ros_camera/` contains the ROS 2 `ament_cmake` package.
- `src/ros_camera/src/camera_node.cpp` is the `camera_node` executable.
- `build/`, `install/`, and `log/` are generated by colcon and are ignored by Git.

## Build and run

Run commands from the workspace root after sourcing a compatible ROS 2 distribution:

```bash
source /opt/ros/<distro>/setup.bash
colcon build --packages-select ros_camera
source install/setup.bash
ros2 run ros_camera camera_node
```

For iterative C++ work, prefer:

```bash
colcon build --packages-select ros_camera --symlink-install
```

If tests are added, run them with:

```bash
colcon test --packages-select ros_camera
colcon test-result --verbose
```

## Development conventions

- Use C++17; the package sets `CMAKE_CXX_STANDARD` to 17.
- Follow ROS 2 Jazzy conventions and use ROS 2 interfaces and parameters where they make behavior configurable.
- Keep the architecture modular: isolate webcam capture, vision processing, and ROS 2 node/interface concerns into focused components as the project grows.
- Add C++ sources under `src/ros_camera/src/` and register each executable in `src/ros_camera/CMakeLists.txt` with `add_executable`, `ament_target_dependencies`, and `install`.
- Declare every build, execution, and test dependency in `src/ros_camera/package.xml` when adding it to CMake or source code.
- Keep ROS node names, executable names, and log messages clear and stable. Use `RCLCPP_*` logging rather than standard output.
- Follow the existing four-space C++ indentation and keep includes minimal and ordered consistently.
- Explain important design or behavior changes before implementing them.

## Before handing off changes

- Build the affected package with `colcon build --packages-select ros_camera` after every change.
- Run package tests when they exist.
- Do not commit `build/`, `install/`, `log/`, editor settings, or other generated files.
- Do not modify unrelated files.
- Keep Git commits small and meaningful.
